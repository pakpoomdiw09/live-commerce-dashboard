## Staging rehearsal and rollout order

1. Build a disposable staging environment from an approved baseline/registry prefix. For a production-like clone, an authorized operator must establish its provenance and protect/redact customer data; this agent's PGlite simulation is not such a clone. Replay the **whole required registry prefix and suffix**, not audit 2 alone. Keep credentials and real Meta transport out of automated fixtures.
2. Capture preflight output and installed public function definitions privately. Confirm the supplied legacy properties and missing timer capabilities. Seed synthetic numeric bidder IDs and a host in isolated staging. Demonstrate legacy immediate order creation before the upgrade; preserve that legacy order for a non-destructive comparison.
3. Quiesce auction writes and worker execution for the staged upgrade. Preserve durable webhook ingress/queueing if supported; do not process queued bids against intermediate financial definitions. Inventory and suspend relevant external/database schedulers through the approved operator process. **The deadlines migration can schedule a pg_cron job if that extension exists** (`live-auction-deadlines.sql:164`–165); account for this side effect before applying it. PGlite has no pg_cron extension and does not exercise hosted job scheduling.
4. Apply missing migrations in registry order with the established ledger/checksum mechanism. The automated rehearsal uses progressively generated **in-memory** complete-schema transactions; stored bundles are untouched. Standalone SQL files contain their own BEGIN/COMMIT: wrapping concatenated files in another transaction is not a substitute for a migration runner's verified atomicity. Do not expose an intermediate deadlines-only installation to writers/workers.
5. Verify old rounds retain NULL deadlines and existing legacy orders are neither deleted nor re-invoiced. Inventory previously created orders separately; no retrospective financial repair is authorized here. Confirm new rounds receive deadlines, explicit timer start is idempotent, not-due is a no-op, pending queue yields draining, and due/no-queue locks a winner without an order.
6. Run the real parser flow: two bidders → trusted host close → no order → genuinely pre-round/older confirmation stale → same-second winner confirmation → one order → replay → still one order. Audit 1 alone should demonstrate the source-seconds race; audit 2 must resolve it. Capture definitions at each stage, compare final definition with a fresh current-source installation, and investigate every unexplained difference.
7. Run privacy/pagination/workspace/financial tests, test the expiry failure ledger/counts, and verify tenant/RLS/grant boundaries. Check application compatibility gates before releasing the app. Run an authenticated cron in staging and inspect `auctionExpiry.failed`/`unavailable`, then confirm the real external scheduler separately. Resume workers/writes only after successful verification.
8. Production execution remains an operator-only follow-up. This task prepares artifacts and local evidence; it neither applies the sequence nor verifies current production state. Keep the identity-unverified phase gate until sanitized real Meta diagnostics arrive.
