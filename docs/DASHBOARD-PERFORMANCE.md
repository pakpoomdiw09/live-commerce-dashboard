# การปรับประสิทธิภาพ Overview และ Commerce

## การติดตั้ง

ติดตั้ง `supabase/dashboard-performance.sql` หลัง `platform.sql`, `billing.sql`, `feature-access.sql`, `smart-inbox.sql`, `agent-control.sql` และ `commerce-v2.sql` ก่อนนำโค้ดชุดนี้ขึ้นใช้งาน ไฟล์รันซ้ำได้ ไม่แก้ไขรายการเดิม เครดิต หรือแพ็กเกจ และไม่เรียกบริการภายนอก

การสร้างดัชนีในไฟล์นี้ใช้ธุรกรรมเดียวกันกับการติดตั้งคำสั่ง SQL สำหรับฐานข้อมูลขนาดใหญ่ ควรติดตั้งในช่วงที่มีการเขียนข้อมูลน้อย เพราะ PostgreSQL จะล็อกการเขียนตารางขณะสร้างดัชนี

ยังไม่ได้ติดตั้งไฟล์นี้ลงฐานข้อมูลจริงจากการพัฒนาครั้งนี้ หากยังไม่ติดตั้ง หน้าจอจะเข้าสู่สถานะโหลดข้อมูลไม่สำเร็จตามเดิม แทนการแสดงยอดจำลองหรือย้อนกลับไปโหลดข้อมูลทั้งหมด

## เส้นทางอ่านข้อมูล

- `overviewFromTables` อ่านข้อมูลร้านหนึ่งรายการและเรียก `overview_dashboard_stats` หนึ่งครั้ง ไม่อ่านลูกค้า ข้อความ และสลิปทั้งหมดเข้า Node.js อีกต่อไป
- ฐานข้อมูลรวมข้อความตามลูกค้า ช่วงเวลา และช่วงชั่วโมงก่อนนำไปคำนวณจำนวนข้อความ ลูกค้า เพศ และกราฟ โดยอ่านเฉพาะข้อความขาเข้าของร้านนั้น
- สลิปใช้ `COUNT`, `SUM` และ `FILTER` รวมยอดปัจจุบันและช่วงก่อนหน้า จำนวนเงินปัดเป็นสตางค์ก่อนรวม รักษาการอนุมัติด้วยตนเองและสถานะเดิม
- รายการแชทและสลิปจำกัดครั้งละ 10 รายการ พร้อมจำนวนรายการทั้งหมด การค้นหาไม่เปลี่ยนยอด KPI ดึงข้อความล่าสุดด้วยดัชนีหลังแบ่งหน้าเมื่อไม่มีคำค้น
- `commerceSnapshot` อ่านข้อมูลร้านหนึ่งรายการและเรียก RPC สองครั้ง ได้แก่ `commerce_dashboard_stats` และ `commerce_dashboard_page` จำนวนคำขอไม่เพิ่มตามจำนวนลูกค้าหรือออเดอร์
- ยอดขาย รายงานรายเดือน สินค้าขายดี จำนวนสินค้า ลูกค้า และออเดอร์คำนวณใน SQL หน้าจอใช้ยอดเหล่านี้แทนการนับรายการในหน้าปัจจุบัน
- รายการสินค้า ออเดอร์ ลูกค้า หมวดหมู่ และเซลเพจจำกัดครั้งละ 50 รายการ เรียงด้วยคอลัมน์หลักและรหัสรายการเพื่อให้ลำดับแน่นอน
- ตัวเลือกสินค้าดึงเฉพาะสินค้าหน้าปัจจุบัน รายการออเดอร์และประวัติดึงแบบชุดเฉพาะออเดอร์หน้าปัจจุบัน จำนวนออเดอร์ของลูกค้าใช้การรวมแบบชุดเฉพาะลูกค้าหน้านั้น ไม่เรียกคำสั่งแยกรายลูกค้า

## ตัวกรอง Commerce

`GET /api/commerce?tenantId=...` รองรับ `productPage`, `orderPage`, `customerPage`, `categoryPage`, `pagePage` (1–1,000), `q` (ไม่เกิน 100 ตัวอักษร), `category` (UUID), `sort` (`new`, `price`, `price_desc`) และ `status` (`all` หรือสถานะออเดอร์ที่ระบบรองรับ)

หน้าร้านค้าเชื่อมลิงก์แบ่งหน้า ตัวกรองสินค้า และสถานะออเดอร์เข้ากับการอ่านฝั่งเซิร์ฟเวอร์ การรีเฟรชหลังบันทึกยังคงตัวกรองและหน้าปัจจุบันไว้ หมวดหมู่สำหรับแก้ไขสินค้ารวมหมวดหมู่ที่สินค้าใช้อยู่ด้วย แม้อยู่นอกหน้ารายการหมวดหมู่

จำกัดเลขหน้าเพื่อไม่ให้คำขอสร้างการอ่าน OFFSET ลึกโดยไม่มีขอบเขต หน้าจอแจ้งเมื่อถึงขอบเขต กรณีร้านมีรายการประเภทเดียวเกิน 50,000 รายการ ควรเพิ่มการแบ่งหน้าด้วยเคอร์เซอร์ก่อนใช้งานกับประวัติส่วนที่ลึกกว่านี้

กราฟ Overview แบบตลอดเวลาแสดงสูงสุด 120 เดือนล่าสุด แต่ KPI ยังคำนวณจากข้อมูลทั้งหมดและมีคำอธิบายบนหน้าจอ รายงาน Commerce แสดง 120 เดือนล่าสุดที่มียอดขาย ประวัติการจัดการที่แนบมากับรายการออเดอร์แสดงล่าสุดสูงสุด 300 รายการตามขอบเขตเดิม

หน้าร้านสาธารณะและการสั่งซื้อ (`publicStore`/`checkout`) คงพฤติกรรมเดิมไว้ การปรับครั้งนี้เปลี่ยนการอ่านแดชบอร์ด ไม่ได้เปลี่ยนตะกร้าหรือราคาที่ใช้ยืนยันคำสั่งซื้อ

## การแยกข้อมูลและสิทธิ์

RPC ทั้งสามให้สิทธิ์เรียกเฉพาะ `service_role` และไม่ใช้ `SECURITY DEFINER` ตัวเรียกเดิมยังตรวจเซสชันและสมาชิกของร้านก่อนเข้าบริการ ทุกการอ่านและ JOIN จำกัดร้าน รวมถึง JOIN ลูกค้าของสลิป ตัวเลือกสินค้า รายการออเดอร์ และประวัติ

Overview ตรวจสิทธิ์ฟีเจอร์ในฐานข้อมูล ส่วนรายงาน Commerce ตรวจแพ็กเกจผ่าน `commerce_plan` และตรวจสิทธิ์ซ้ำในบริการ ตัวกรองจากเบราว์เซอร์ไม่สามารถเปิดรายงานหรือเปลี่ยนร้านที่ผ่านการตรวจสิทธิ์แล้ว

มีดัชนีประกอบร้าน/เวลา/รหัส สำหรับสลิป ลูกค้า ข้อความ งาน AI ออเดอร์ สินค้า และประวัติ รวมถึงดัชนีสำหรับสถานะออเดอร์ วันที่ชำระเงิน และรายการย่อย

การนับแบบครบถ้วนยังมีต้นทุนตามจำนวนข้อมูลในร้าน โดยเฉพาะตัวเลือกตลอดเวลา การค้นหาข้อความแบบส่วนหนึ่งของคำยังสแกนข้อมูลภายในร้านและช่วงวันที่ที่เลือก ไม่มีการอ้างว่าจำนวนการอ่านภายในฐานข้อมูลเป็นค่าคงที่

## ผลการตรวจสอบ

การทดสอบที่เกี่ยวข้องผ่านรวม 20 กรณี (ชุด Commerce/Performance 15 กรณี และ Overview ที่เลือกตรวจ 5 กรณี) และ Build ผ่าน มีคำเตือน ESLint เดิมของโปรเจกต์

- `node --test scripts/test-dashboard-performance.cjs scripts/test-dashboard-performance-sql.cjs scripts/test-commerce.cjs scripts/test-commerce-sql.cjs`
- `node --test --test-name-pattern="direct slip|search paginates|overview uses|overview carries|Avatar renders" scripts/test-feature-restoration.cjs`
- `npm run build`

ทดสอบ SQL จริงด้วย PostgreSQL/WASM แยกจากระบบจริง: ข้อมูล 1,205 รายการ การปัดเศษยอดเงิน ช่วงเปรียบเทียบ เวลาไทย การแบ่งหน้าไม่ทับกัน ข้อมูลหลายร้าน สิทธิ์ RPC การรัน migration ซ้ำ ฟิลด์โปรไฟล์เสริมที่ไม่มีในฐานข้อมูลเก่า และแผนอ่านข้อความล่าสุดที่ใช้ดัชนี

การรันชุดเก่ารวม `test-feature-restoration.cjs` และ `test-premium-overview.cjs` พบ 6 กรณีที่ใช้ fixture ไม่ตรงกับระบบปัจจุบัน ได้แก่ mock `AiTestingStudio`, mock `supabaseAdmin().from`, และ dependency `ui-labels` ของ Overview จึงไม่ถือว่าชุดทดสอบทั้งโปรเจกต์ผ่านทั้งหมด การปรับครั้งนี้ไม่เปลี่ยนพฤติกรรมผลิตภัณฑ์เพื่อให้ตรงกับ fixture เก่าเหล่านั้น
