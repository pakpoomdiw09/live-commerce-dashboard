# ความถูกต้องของเวลาข้อความ Facebook

ใช้กับ `/api/webhook/facebook`, URL เดิม `/api/webhooks/facebook` และ worker ของคิวถาวรจาก Part 1 ทั้งสอง URL ใช้ handler และเงื่อนไขตรวจเวลาเดียวกัน

## ติดตั้ง

รัน `supabase/facebook-message-window.sql` หลัง `supabase/smart-inbox.sql` และ `supabase/facebook-webhook-queue.sql` ก่อนนำโค้ด Part 2 ขึ้นใช้งาน ไฟล์นี้รันซ้ำได้ ไม่เปลี่ยนเวลาที่เก็บไว้เดิม ไม่ส่งข้อความ และไม่เปลี่ยนโหมดความปลอดภัย

สำหรับการติดตั้งใหม่ ไฟล์ `facebook-webhook-queue.sql` มีการตรวจสอบและคำสั่งบันทึกเวอร์ชันเดียวกันแล้ว ส่วน `smart-inbox.sql` ถูกปรับให้การรันซ้ำไม่คืนพฤติกรรมใช้เวลาท้องถิ่นสำหรับข้อความ Facebook

## การตรวจสอบข้อความ

- รับข้อมูลจากคิวที่ผ่าน HMAC-SHA256 แล้วเท่านั้น ใช้ `event.timestamp` หน่วยมิลลิวินาทีเป็นเวลาข้อความ
- ผู้ส่งต้องเป็นรหัสผู้ใช้ ไม่ใช่เพจ และผู้รับต้องตรงกับเพจในเหตุการณ์
- ต้องมี message ID และเนื้อหาข้อความที่ไม่ว่าง หรือสื่อประเภทที่รองรับพร้อม payload
- ไม่ใช้ echo, deleted/unsupported message, delivery/read receipt, postback, referral, reaction หรือเหตุการณ์ควบคุมระบบเป็นหลักฐานต่ออายุช่วงตอบกลับ
- timestamp ต้องเป็นจำนวนเต็มบวกที่ปลอดภัย และต้องไม่อยู่หลังเวลาที่ฐานข้อมูลรับเหตุการณ์นั้นครั้งแรก ไม่มี fallback ไปใช้ `Date.now()`, เวลาเริ่ม worker หรือ `messages.created_at` ที่สร้างในภายหลัง
- เวลารับครั้งแรกใช้เป็นเพดานตรวจสอบเท่านั้น จึงไม่มีเหตุการณ์อนาคตที่กลับกลายเป็นเหตุการณ์ใช้ได้เพียงเพราะ worker ประมวลผลช้า

TypeScript ตรวจสอบก่อนประมวลผล และฟังก์ชัน PostgreSQL ตรวจซ้ำจาก payload ที่เก็บในคิว เหตุการณ์ที่ไม่ผ่านยังคงมี raw payload สำหรับตรวจสอบ และบันทึก checkpoint เป็น `ignored` โดยไม่สร้างข้อความลูกค้าหรือขยายช่วงตอบกลับ

## การอัปเดตแบบ atomic

การสร้างข้อความและอัปเดต `last_message_at` อยู่ในธุรกรรมเดียวกัน อัปเดตเฉพาะเมื่อ insert ข้อความใหม่สำเร็จ และเวลาจาก Meta ใหม่กว่าค่าปัจจุบัน หรือค่าปัจจุบันยังว่าง

ข้อความที่มาถึงสลับลำดับยังเก็บเวลาตามเหตุการณ์จริง ข้อความที่เก่าเกิน 24 ชั่วโมงยังคงเก่า จึงไม่เปิดช่วงตอบกลับใหม่จากเวลาที่เซิร์ฟเวอร์เพิ่งได้รับ ส่วนข้อความซ้ำไม่ทำให้เวลาหรือจำนวนข้อความเพิ่มขึ้นจากเส้นทางบันทึกนี้

trigger `inbox_incoming_message` ยังคงจัดการลำดับข้อความและสถานะห้องแชท แต่ไม่ใช้ `created_at` ต่ออายุช่วงตอบกลับของ Facebook ช่องทางอื่นคงพฤติกรรมเดิม

ข้อมูลเก่าที่อาจเคยได้เวลาไม่ถูกต้องจะไม่ถูกเดาหรือแก้ย้อนหลังอัตโนมัติ การแก้ข้อมูลเก่าต้องอาศัยหลักฐานเวลาจาก Meta ที่ตรวจสอบได้

## สถานะ Webhook ในหน้า Settings

หน้า Settings แสดงเวลาข้อความ inbound ล่าสุดจาก `broadcast_messaging_events` ซึ่ง webhook worker บันทึกหลังตรวจสอบและ persist เหตุการณ์ที่ลงนามแล้ว หากยังไม่มีหลักฐาน ให้ส่งข้อความใหม่ถึงเพจและตรวจสอบ worker/การติดตั้ง schema; หากอ่านตารางไม่ได้ หน้า Settings จะแสดงสถานะตรวจสอบไม่ได้แทนการสรุปว่าไม่มีข้อความเข้า

## การส่งข้อความจาก Inbox

การตอบกลับปกติใช้ `RESPONSE` และยังอยู่ภายใต้ช่วงเวลาตอบกลับ 24 ชั่วโมง ระบบไม่เพิ่ม `MESSAGE_TAG` เพื่อเลี่ยงข้อจำกัดนี้ การใช้ `HUMAN_AGENT` ทำได้เฉพาะการตอบโดยแอดมิน เมื่อเปิดการอนุมัติไว้ และมีหลักฐาน inbound ภายในช่วงเวลาที่ Meta อนุญาต หาก Graph API ปฏิเสธ ระบบบันทึก HTTP status, error code/subcode และข้อความที่ผ่านการปกปิดข้อมูลสำคัญลง Terminal

## ทดสอบ

```sh
node --test scripts/test-facebook-webhook-queue.cjs
npm run build
```

ชุดทดสอบใช้บริการจำลองและ PostgreSQL ผ่าน PGlite ครอบคลุม timestamp ผิดชนิด/อนาคต ความละเอียดมิลลิวินาที ข้อความซ้ำ เหตุการณ์สลับลำดับ ข้อความเก่า สื่อ ข้อความระบบ echo receipt และ trigger จริง โดยไม่เรียก Facebook หรือแก้ฐานข้อมูลจริง
