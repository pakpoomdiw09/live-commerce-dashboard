# ตั้งค่าระบบดูดออเดอร์ไลฟ์สด

กด “เลือกจากไลฟ์สดปัจจุบัน” เพื่อเปิดหน้าต่างรายการไลฟ์ของเพจที่เลือก มีรูปย่อ หัวข้อ เวลาเริ่มตามเวลาไทย ป้าย LIVE และปุ่มรีเฟรช รองรับสถานะกำลังโหลด ไม่มีไลฟ์ และข้อผิดพลาด เมื่อเลือกจะแสดงการ์ดและใส่รหัสไลฟ์ให้ทันที เปลี่ยนเพจแล้วล้างไลฟ์เดิมเพื่อไม่ให้ใช้รหัสข้ามเพจ กด “กรอกรหัสด้วยตนเอง” เพื่อวางลิงก์แบบเดิมได้

`GET /api/facebook/live-videos?page_id=...` ตรวจการเข้าสู่ระบบและสิทธิ์เจ้าของร้านก่อนอ่าน `tenants.page_access_token` ใช้โทเคน/ตัวเลือกสำรองที่จำกัดเพจเดียวกันกับระบบรับคอมเมนต์ ไม่มีโทเคนถูกส่งกลับ browser จำกัดรีเฟรช 12 ครั้งต่อนาทีต่อผู้ใช้/ร้านผ่าน `commerce_rate_limit` เดิม และไม่ cache ผลลัพธ์หรือข้อผิดพลาด ไม่ต้องเพิ่ม migration

ก่อนอ่านวิดีโอ API เรียก `/debug_token` ตรวจ `is_valid`, ชนิด `PAGE`, `profile_id` ตรงกับเพจ, วันหมดอายุ และสิทธิ์ `pages_read_engagement` หากเป็น User Access Token หรือโทเคนของเพจอื่นจะปฏิเสธและแสดงสาเหตุ โดยไม่แลกโทเคนหรือเปลี่ยนค่าที่บันทึกอัตโนมัติ การตรวจใช้ app credential จาก `FB_APP_ID`/`FB_APP_SECRET` เมื่อมี มิฉะนั้นใช้โทเคนเดิมตรวจ และปฏิเสธหากยืนยันชนิดไม่ได้

การดึงรายการลอง `/live_videos` พร้อม `broadcast_status=["LIVE"]` ก่อน แล้วลองแบบไม่กรองหากว่างหรือ Meta ไม่รองรับตัวกรอง ใช้ `limit=10` ต่อหน้า รับสถานะ `LIVE`/`LIVE_NOW` หรือ `live_views > 0` เฉพาะรายการที่ไม่ระบุสถานะ ไม่ใช้ยอดผู้ชมเก่าของสถานะ `VOD`/`LIVE_STOPPED` เป็นหลักฐานว่าไลฟ์อยู่ หาก Meta ไม่รองรับฟิลด์เสริมจะลองเฉพาะฟิลด์หลัก หากยังไม่พบ LIVE จะอ่าน `/videos?limit=3` เป็นรายการสำรอง โดยใช้ `created_time`/`picture` ของวิดีโอตาม [SDK ทางการของ Meta](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/advideo.py) ผลลัพธ์มี `fallback` และ `isLive` ให้หน้าต่างกับพรีวิวติดป้ายวิดีโอสำรอง ไม่แสดงเป็น LIVE

ดู server/Vercel Function Logs ชื่อ `[facebook/live-videos] Graph response` เพื่อดู `edge`, HTTP `status` และ `raw` ว่า Meta ส่ง `error` หรือ `data: []` บันทึกทุกผลตอบกลับโดยปิดบัง Page Token, App Secret, Authorization, stream URLs และโทเคนใน paging URLs ก่อนเสมอ ข้อความ OAuthException ส่งถึงหน้าบ้านพร้อมรหัสและเหตุผลจาก Meta ที่ปิดบังข้อมูลลับแล้ว ข้อผิดพลาดสิทธิ์/โทเคนไม่ถูกกลบด้วยรายการสำรอง

ยังแบ่งหน้าโดยใช้ cursor สร้าง URL ฝั่งเซิร์ฟเวอร์เอง มี timeout และลองใหม่หนึ่งครั้งเมื่อเครือข่ายหรือเซิร์ฟเวอร์มีปัญหา หาก LiveVideo มี `video.id` จะใช้รหัสวิดีโอจริงนั้นเป็น `id` เพื่อให้ตรงกับโพสต์ใน webhook แล้วส่งผ่าน `livePostId` ไปบันทึก `comment_rules.live_post_id` ตามสัญญา API เดิม

หน้า `/live-cf` รับลิงก์วิดีโอ Facebook แบบเต็ม เช่น `/ชื่อเพจ/videos/123...`, `/watch/?v=123...`, `/watch/live/?v=123...` และ `/video.php?v=123...` เมื่อวางลิงก์หรือออกจากช่องกรอก ระบบจะเปลี่ยนเป็นรหัสให้ทันที ยังรองรับรหัสตัวเลขและ `เพจ_โพสต์` เดิม การเว้นว่างหมายถึงรับทุกไลฟ์ของเพจ ลิงก์ย่อ `fb.watch` และลิงก์แชร์ที่ไม่มีรหัสตัวเลขจะให้คัดลอกลิงก์วิดีโอแบบเต็ม ไม่เดารหัสจากข้อความในลิงก์

หัวข้อ “2. กำหนดคีย์เวิร์ดดูดออเดอร์ (Keywords)” รองรับ 1–5 แท็ก พิมพ์รหัสแล้วกด Enter หรือ “เพิ่มรหัส” แต่ละแท็กลบได้ด้วยปุ่มกากบาท เมื่อครบ 5 รหัสจะปิดการเพิ่มและแสดง “เพิ่มได้สูงสุด 5 รหัส” ป้องกันรหัสว่างและรหัสซ้ำ รวมถึงตัวพิมพ์เล็ก/ใหญ่และอักขระเทียบเท่ากัน เช่น `A1`, `a1`, `Ａ１` ถือเป็นรหัสเดียวกันตามการจับคู่เดิม รหัสยาวไม่เกิน 40 ตัว รองรับตัวอักษร/ภาษาไทย ตัวเลข ขีดกลาง และขีดล่าง โดยไม่มีช่องว่าง

ทุกครั้งที่เปิดหน้า ช่องสินค้าเริ่มที่ “เลือกสินค้า” แม้มีกฎเดิมหรือสินค้าในร้านแล้ว พรีวิวสินค้าและข้อมูลสินค้าในสรุปจะแสดงหลังผู้ใช้เลือกเองเท่านั้น การเพิ่มสินค้าใหม่ผ่านหน้าต่างยังเลือกสินค้าที่เพิ่งบันทึกให้ทันที หากยังไม่เลือกสินค้าจะไม่ส่งคำขอเปลี่ยนสถานะระบบไปยัง API

กฎใหม่เริ่มด้วยรายการรหัสและช่องทดลองว่าง ไม่มีรหัสตัวอย่างเติมให้อัตโนมัติ ส่วนการเปิดแก้ไขยังแสดงรหัสที่เคยบันทึกไว้ เมื่อเลือกสินค้า ระบบแทนที่ชุดคีย์เวิร์ดเดิมด้วย `sku` ที่ไม่ว่าง หรือใช้ `code` เป็นแท็กแรก หากไม่มีทั้งคู่จะปล่อยว่าง ผู้ใช้ลบหรือเพิ่มคำเองต่อได้สูงสุด 5 คำ ตัวอย่างเปลี่ยนทันที เช่น `A1`, `รับ A1`, `จอง A1`, `เอา A1`, `A1 ครับ`, `A1 ค่ะ` เมื่อช่องและรายการรหัสว่างจะแสดง “กรุณากรอกรหัสสินค้าเพื่อดูตัวอย่าง” สินค้าที่เพิ่งสร้างผ่านหน้าต่างนำรหัสที่ผู้ใช้กรอกมาเลือกให้เช่นกัน

State ใช้ `codes: string[]` และส่งใน `POST /api/live-cf/setup` เช่น `{ "codes": ["A1", "159", "จอง"] }` เซิร์ฟเวอร์ตรวจซ้ำแล้วบันทึกทุกค่าใน `comment_rules.keywords` เดิม ไม่ต้องเพิ่ม migration การอ่านกฎเดิมโหลดทุกแท็กกลับมา ส่วนผู้เรียก API รุ่นเก่าที่ส่ง `code` เดียวยังใช้งานได้ หากส่ง `codes` ที่ผิดรูปแบบจะตอบ 400 โดยไม่ย้อนกลับไปใช้ `code` แทน

ตัวอย่างคำสั่งซื้อและกล่องทดลองคอมเมนต์ตรวจทุกรหัสด้วย `matchLiveCfCode` ตัวเดียวกับ webhook โหมด Contains (`flexible`) จับคีย์เวิร์ดที่อยู่ส่วนใดก็ได้ของข้อความ รวมถึงบางส่วนของคำหรือตัวเลข เช่น `159` ใน `cf159?` และ `1590` ไม่แยกตัวพิมพ์เล็ก/ใหญ่ ตัดเครื่องหมายพิเศษท้ายข้อความ และรองรับช่องว่างระหว่างตัวอักษรกับตัวเลข เช่น คีย์เวิร์ด `CF159` จับ `cf159?` และ `เอา cf 159` ได้ เก็บเครื่องหมาย `_` / `-` ที่เป็นส่วนของรหัสและศูนย์นำหน้าไว้ โหมด Exact Match (`strict`) ยังต้องตรงทั้งข้อความ โดยไม่ตัดเครื่องหมายท้ายคำหรือรวมช่องว่างภายใน

หน้าตั้งค่าส่ง `matchMode` ไปยัง API ซึ่งบันทึก `comment_rules.match_type` เป็น `keyword` สำหรับ Contains หรือ `exact` สำหรับ Exact Match การโหลดกฎกลับมาใช้ค่านี้เลือก matcher จึงไม่ต้องเพิ่มคอลัมน์หรือ migration หากพิมพ์รหัสสุดท้ายค้างไว้แล้วกดบันทึก ระบบจะตรวจและเพิ่มรหัสนั้นก่อนส่ง เพื่อไม่ให้ข้อความที่กรอกไว้หายไป

กด “เพิ่มสินค้าใหม่เข้าเซลล์เพจ” ข้างช่องเลือกสินค้าเพื่อกรอกรหัสสินค้า ชื่อ หมวดหมู่ ราคาขาย รายละเอียด และสต็อกรวม อัปโหลดรูปได้ 8 รูป พร้อมภาพย่อขนาด 80 พิกเซล แสดงเฉพาะรูปที่เพิ่มและปุ่มเพิ่มรูปถัดไป หน้าต่างใช้โทนขาว/เทาอ่อนและเส้นขอบบาง ไม่มีช่องต้นทุน ราคาเปรียบเทียบ หรือ checkbox สถานะขาย/สินค้าแนะนำ บันทึกโดยเปิดขายเสมอและไม่ตั้งเป็นสินค้าแนะนำ (`is_active: true`, `featured: false` ซึ่งตรงกับ `products.commerce_featured` ในฐานนี้)

หน้าต่างกว้าง `max-w-3xl` เลื่อนเฉพาะตัวฟอร์มได้โดยหัวข้อและปุ่มบันทึกยังอยู่กับที่ ปุ่มยกเลิกและบันทึกอยู่ด้านล่างขวา บันทึกสำเร็จจะเลือกสินค้า เติมรหัสจอง และแสดงรูป/ราคา/สต็อกในสรุปโดยไม่โหลดหน้าใหม่

ตัวเลือกเพิ่มได้ 2 กลุ่ม เช่น สี (ขาว, ดำ) และขนาด (S, M) ระบบสร้างชุดย่อยครบทุกคู่ รวมไม่เกิน 40 แบบ ราคาและสต็อกแต่ละแบบไม่บังคับกรอก ราคาว่างใช้ราคาหลัก ณ ตอนบันทึก สต็อกว่างแบ่งจากสต็อกรวมที่เหลือให้แต่ละแบบอย่างเท่าๆ กัน โดยไม่เพิ่มจำนวนสินค้ารวม หากระบุสต็อกครบทุกแบบ จะใช้ผลรวมเป็นสต็อกหลัก ค่า `0` เป็นสต็อกศูนย์จริง มีเพียงค่าว่างที่ใช้การแบ่งอัตโนมัติ ไม่มีช่องรหัส CF ย่อย

สำหรับสินค้าที่มีตัวเลือก หน้าไลฟ์ใช้รหัสหลักสร้างรายการจอง โดยยังไม่เลือกสี/ขนาดและจองเฉพาะสต็อกรวม ลูกค้าเปิดลิงก์ HMAC ใน `/pay/live/[token]` แล้วเลือกแบบและยืนยันก่อนเห็นข้อมูลโอนเงิน เซิร์ฟเวอร์ตรวจตัวเลือกของสินค้า/ร้านเดียวกัน ล็อกและลดสต็อกตัวเลือกพร้อมเปลี่ยนยอดใน transaction เดียว การยืนยันซ้ำแบบเดิมไม่หักสต็อกอีก เมื่อยืนยันแล้วราคาและตัวเลือกถูกล็อก หากต้องแก้ไขต้องติดต่อร้านค้า รายการที่ยกเลิกคืนเฉพาะสต็อกที่เคยจองจริง

หากลูกค้ามีหลายรายการค้าง ระบบรอให้ยืนยันตัวเลือกครบทุกลิงก์ก่อนแสดงยอดรวมที่ต้องโอน ยอดอิงรายการค้างจริงตามระบบตรวจสลิปเดิม ทั้งการรับสลิป valid และการเปลี่ยนออเดอร์ paid ตรวจยอดปัจจุบันอีกครั้ง เพื่อป้องกันยอดเดิมจ่ายสินค้าที่ราคาเปลี่ยนหลังเลือกตัวเลือก

**ต้องติดตั้งก่อน deploy:** รัน [live-cf-customer-variants.sql](../supabase/live-cf-customer-variants.sql) หลัง `live-cf-setup.sql`, `payments.sql`, `payment-pro.sql` หรือรัน [complete_schema.sql](../supabase/complete_schema.sql) รุ่นล่าสุดซึ่งรวม migration นี้แล้ว เป็น migration เพิ่มคอลัมน์/ฟังก์ชันและ guards ไม่แก้ประวัติ migration เดิม ไม่ได้ apply ไปยังฐานจริงระหว่างพัฒนา

## ไฟล์ที่เกี่ยวข้อง

ปุ่ม “แก้ไขสินค้านี้” บนการ์ดเปิด `QuickProductModal` ด้วย `initialData` เปลี่ยนหัวข้อเป็น “แก้ไขข้อมูลสินค้า” และปุ่มเป็น “บันทึกการแก้ไข” อ่านข้อมูลเต็มจาก `GET /api/commerce/products/[id]?tenantId=...` ซึ่งตรวจสิทธิ์เจ้าของร้านและกรองทั้งสินค้า/ตัวเลือกตามร้านก่อนคืนรูปทั้งหมด หมวดหมู่ ราคา สต็อก และ `commerce_version` การบันทึกส่ง `id`/`version` เข้า `POST /api/commerce` เดิมให้ `commerce_save_product` อัปเดตสินค้าและตัวเลือกใน transaction เดิม เก็บต้นทุน ราคาเปรียบเทียบ สถานะขาย สินค้าแนะนำ และรหัสตัวเลือกที่ไม่ได้เปิดให้แก้ในหน้าต่างไว้ ไม่ต้องเพิ่ม migration

ตัวเลือกที่มีป้ายสี/ขนาดแบบครบทุกคู่จะคืนเป็นกลุ่มเดิม ส่วนรายการเก่าหรือชุดที่ไม่ครบทุกคู่แสดงเป็นแถวชื่อ/ราคา/สต็อกเดิมเพื่อไม่สร้างตัวเลือกเพิ่มเอง รักษา UUID ของตัวเลือกที่ยังอยู่ หากเวอร์ชันสินค้าเปลี่ยน API ตอบ 409 และมีปุ่มโหลดข้อมูลล่าสุดก่อนบันทึกใหม่ เมื่อสำเร็จอัปเดตสินค้ารหัสเดิมใน Dropdown และพรีวิวโดยไม่ refresh หน้า หาก SKU เปลี่ยนจะปรับคีย์เวิร์ดตามรหัสใหม่ หากแก้เฉพาะชื่อ/ราคาโดย SKU ไม่เปลี่ยนจะรักษาคีย์เวิร์ดที่ผู้ใช้ปรับเองไว้

การเพิ่มสินค้าใช้ `POST /api/commerce` เดิมด้วย `action: product` ซึ่งตรวจเจ้าของร้าน ต้นทางคำขอ ข้อมูลสินค้า จำนวนรายการตามแพ็กเกจ และรหัสซ้ำ ก่อนเรียก `commerce_save_product` ให้บันทึก `products` และ `commerce_variants` ใน transaction เดียว กำหนด UUID ของตัวเลือกก่อนส่งเพื่ออ้างอิงรายการที่ตรงกับฐานข้อมูล ไม่มี service key ใน browser

หมวดหมู่โหลดจาก `commerce_categories` โดยกรอง `tenant_id` และแบ่งหน้าให้ครบ แล้วรวมหมวดหมู่มาตรฐานแบบเดียวกับหน้าร้าน หากโหลดไม่สำเร็จสามารถลองใหม่ได้โดยไม่เสียข้อมูลฟอร์ม รูปส่งไป `POST /api/commerce/media` เดิม ซึ่งตรวจไฟล์และสิทธิ์ก่อนแปลงภาพเป็น WebP แล้วเก็บใน Supabase Storage bucket `comment-media` ที่ `commerce/{tenantId}/...` URL ของรูปบันทึกใน `products.commerce_images` และรูปแรกใน `products.image_url` ตามโครงสร้างเดิม ปุ่มบันทึก/ปิดจะรอจนการอัปโหลดเสร็จ

รหัส CF จากฟอร์มบันทึกลง `products.code` ซึ่งเป็นคอลัมน์รหัสสินค้าจริงของโปรเจกต์นี้ ค่าเริ่มต้นคือเปิดขายและ `commerce_archived: false` เพื่อให้สินค้าแสดงในเซลเพจโดยอัตโนมัติเมื่อเปิดหน้าร้านและมีส่วนรายการสินค้าอยู่แล้ว ไม่เปิดหน้าร้านที่ปิดอยู่แทนผู้ใช้ ต้องเปิดระบบร้านค้าและจัดการสินค้าเดิม (`NEXT_PUBLIC_SALES_PAGE_V2_ENABLED=true` และไม่ตั้ง `PRODUCT_MANAGER_V2_ENABLED=false`)

ข้อความบนหน้าจอใช้ `{ชื่อสินค้า}`, `{ราคา}`, `{ตัวเลือกสินค้า}`, `{ยอดชำระ}` และ `{ลิงก์ชำระเงิน}` โดยแปลงกลับเป็นคำแทนข้อมูลภาษาอังกฤษเดิมก่อนบันทึก จึงยังส่งข้อความผ่านระบบเดิมได้และเปิดแก้ไขข้อความเก่าได้
