# จำกัดขนาดและหน่วยความจำระหว่างอัปโหลด

ขอบเขต: `app/api/commerce/media/route.ts`, `app/api/slips/verify/route.ts` และเครื่องมือร่วม `lib/upload-security.ts` ไม่เปลี่ยนฐานข้อมูล ไม่เปลี่ยนเครดิตหรือสิทธิ์แพ็กเกจ และไม่ต้องตั้งค่าตัวแปรเพิ่ม

## ขอบเขตทรัพยากร

| รายการ | ขีดจำกัด |
| --- | --- |
| ไฟล์ภาพ | 5 MiB (5 × 1,024 × 1,024 ไบต์) |
| คำขอ multipart ทั้งหมด | ขนาดไฟล์ + 64 KiB สำหรับส่วนหัวและช่องข้อความ |
| ความละเอียดภาพที่ถอดรหัส | 16 ล้านพิกเซล |
| เวลาอ่านสตรีมทั้งหมด | 15 วินาที |
| จำนวนชิ้นข้อมูลจากสตรีม | 16,384 ชิ้น |
| เวลาแปลง/ตรวจภาพด้วย Sharp | 5 วินาทีต่อการประมวลผล |
| งานพร้อมกันใน Node runtime เดียว | 2 งาน รวมสองเส้นทาง |
| งานพร้อมกันต่อผู้ใช้ใน runtime เดียว | 1 งาน |
| ส่วนหัวต่อ multipart part | 4 KiB |
| QR | 4 KiB |

Commerce ยังตรวจเจ้าของร้านและอัตราการอัปโหลดจากฐานข้อมูลก่อนอ่านไฟล์ ส่วนตรวจสลิปยังตรวจผู้ใช้ก่อนอ่านข้อมูล ตรวจร้านและแพ็กเกจก่อนถอดรหัสภาพ และตรวจสลิปผ่านกระบวนการเดิม

## ลำดับการอ่าน

1. จองช่องทำงานแบบไม่ต่อคิว หากเต็มตอบ 429 พร้อม `Retry-After` การจองใช้สถานะร่วมผ่าน `Symbol.for` บน `globalThis` เพื่อให้สอง route ใช้ขอบเขตเดียวกันแม้แยก bundle
2. ตรวจ Content-Type, boundary และ Content-Encoding ไม่รับคำขอ gzip/br โดยตรง ใช้ Content-Length เป็นเพียงการปฏิเสธล่วงหน้าเมื่อเห็นว่ามากเกินกำหนด
3. อ่าน `request.body` โดยนับจำนวนไบต์จริงลงพื้นที่พักที่มีขนาดตายตัว ไม่สะสมรายการ chunks ที่ขยายได้ เมื่อเกินขนาด ยกเลิก reader และตอบ 413 แม้ไม่ส่ง Content-Length หรือส่งค่าต่ำกว่าจริง
4. จำกัดเวลาและจำนวนครั้งที่อ่าน ไม่มีการผูก callback ซ้ำกับ promise สำหรับ timeout ทุก chunk จึงไม่สะสม pending handlers จากคำขอที่แบ่งข้อมูลเป็นชิ้นเล็กมาก
5. ตรวจโครงสร้าง multipart ในข้อมูลที่จำกัดขนาดแล้ว ก่อนเรียก parser: ไม่รับช่องนอกสัญญา ช่องซ้ำ header ยาว ชื่อช่องกำกวม หรือข้อมูลไม่ครบ ตรวจขนาดไฟล์และข้อความแต่ละช่องก่อน parser สร้าง File/FormData
6. เรียก `formData()` บน Request ภายในที่สร้างจากข้อมูลจำกัดขนาดแล้วเท่านั้น ไม่เรียกบนคำขอขาเข้า ตรวจชื่อ ชนิด และขนาดของช่องซ้ำหลัง parser เพื่อป้องกันการตีความต่างกัน
7. ตรวจ magic bytes ของ JPEG/PNG/WebP ให้ตรงกับ MIME ที่ประกาศ ตรวจด้วย Sharp และทดลองถอดรหัส ปฏิเสธภาพเสีย ภาพเคลื่อนไหว และภาพเกินขีดจำกัดพิกเซล จากนั้นจึงส่งต่อ storage/ผู้ให้บริการ
8. คืนช่องทำงานใน `finally` ทุกทางออก รวมถึง parse ไม่ผ่าน ผู้ใช้ยกเลิก ตรวจภาพไม่ผ่าน และผู้ให้บริการขัดข้อง

Commerce ยังคงแปลงรูปเป็น WebP สูงสุด 2,000 × 2,000 พิกเซล ลบ metadata และใช้ชื่อสุ่มภายใต้ร้าน ส่วนสลิปส่งไฟล์เดิมที่ตรวจแล้วให้กระบวนการยืนยัน เพื่อรักษาการตรวจหลักฐาน/สลิปซ้ำ

ขอบเขตนี้จำกัดการอ่านและงานของแอปต่อ runtime ไม่ใช่ขอบเขตจำนวนคำขอรวมทุก instance และไม่สามารถยกเลิกการรับ/พักข้อมูลที่ reverse proxy หรือแพลตฟอร์มทำก่อนส่งคำขอถึง route ได้ ขอบเขตการรับข้อมูลที่ชั้นนั้นและการจำกัดอัตรารวมยังขึ้นกับโฮสต์ที่ใช้งาน

## สถานะตอบกลับ

- 400: multipart ผิดรูปแบบ ช่องซ้ำ ข้อมูลขาด ไฟล์ว่าง หรือการอัปโหลดถูกยกเลิก
- 408: อ่านข้อมูลนานเกินกำหนด
- 413: คำขอ ไฟล์ ช่องข้อความ ความละเอียดภาพ หรือจำนวนชิ้นสตรีมเกินขอบเขต
- 415: Content-Type/encoding ไม่รองรับ MIME ไม่ตรงเนื้อหา หรือภาพเสีย/เคลื่อนไหว
- 429: ช่องทำงานเต็ม หรือเกินอัตราอัปโหลด Commerce เดิม

## การตรวจสอบ

```text
node --test scripts/test-upload-security.cjs scripts/test-commerce-media.cjs scripts/test-feature-access-api.cjs
npm run build
```

ทดสอบสตรีมจริงและ Sharp จริง ไม่ใช้ผู้ให้บริการหรือฐานข้อมูลจริง: ไม่มี/ปลอม Content-Length, หยุดอ่านและ cancel เมื่อเกินขนาด, timeout/disconnect, multipart จำนวนมากหรือผิดรูปแบบ, ขนาดแต่ละช่อง, ไฟล์ปลอม/เสีย, pixel bomb, animated WebP, จำนวนงานพร้อมกันและการคืนช่อง รวมถึงการอัปโหลดจริงที่ยังลบ metadata และบันทึกภายใต้ร้าน ตลอดจน QR และการปฏิเสธแพ็กเกจเดิม
