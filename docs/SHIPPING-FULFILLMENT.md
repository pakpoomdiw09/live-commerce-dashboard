# ระบบจัดส่งพัสดุ SnapBot

หน้า `/shipping` อยู่ใน Sidebar รองรับบิลสะสมจาก CF/ประมูลและออเดอร์เดี่ยวที่มีสถานะชำระแล้ว มีตัวกรอง Session, รอที่อยู่, พร้อมส่ง, เปิดพิมพ์แล้ว, ส่งแล้ว และยกเลิก เลือกทำรายการเป็นชุดได้สูงสุด 100 พัสดุ

## ติดตั้งและเริ่มใช้

1. ฐานข้อมูลเดิมให้รัน `supabase/shipping-fulfillment.sql` **หลัง** `supabase/live-session-dashboard.sql` และ migration ที่เป็น prerequisite หากเป็นฐานข้อมูลใหม่ ใช้ `supabase/complete_schema.sql` ซึ่งรวมทุก migration แล้ว
2. Deploy โค้ดเวอร์ชันนี้พร้อม Webhook handler ระบบใช้ Supabase และ Page token เดิม ไม่ต้องตั้ง API ขนส่งเพื่อ Export หรือพิมพ์
3. เปิด `/shipping` แล้วตั้งค่าชื่อร้าน เบอร์โทร และที่อยู่ผู้ส่ง เจ้าของร้านเป็นผู้บันทึกการตั้งค่านี้ สมาชิก staff จัดการผู้รับ เลขพัสดุ พิมพ์ และ Export ได้ภายในร้านที่มีสิทธิ์
4. เมื่อบิลชำระครบ ระบบเพิ่มรายการจัดส่งเอง รอข้อมูลที่อยู่จาก Messenger หรือกรอกจากปุ่มแก้ไขผู้รับ ตรวจและยืนยันข้อมูลก่อนออกฉลาก
5. เลือกพัสดุแล้วพิมพ์สติกเกอร์/A4 หรือ Export CSV ถ้าไม่เลือก ระบบใช้รายการพร้อมส่งในตัวกรองปัจจุบันสูงสุด 100 รายการ
6. นำ CSV ไปนำเข้าระบบขนส่งตามที่ร้านใช้งาน บันทึกเลข Tracking กลับมา แล้วเลือก “อัปเดตเป็นส่งพัสดุแล้ว” การ Export และพิมพ์ไม่เปลี่ยนสถานะเป็นส่งแล้วอัตโนมัติ

## การรวมรายการและสถานะ

`shipping_shipments` เป็นพัสดุจริง และ `shipping_shipment_items` กำหนดให้ออเดอร์หนึ่งอยู่ในพัสดุได้เพียงชุดเดียว รายการใน Customer Tab ที่ชำระครบรวมลงพัสดุที่ยังไม่ส่งของบิลนั้น รายการใหม่ที่ชำระหลังส่งกล่องเดิมแล้วสร้างพัสดุใหม่ ฉลากและที่อยู่ของกล่องที่ส่งแล้วไม่เปลี่ยน

เพิ่มคอลัมน์ `recipient_name`, `phone_number`, `shipping_address`, `tracking_number`, `courier_name`, `fulfillment_status`, `label_printed_at` และ `shipping_shipment_id` ใน `orders`/`customer_tabs` โดย mirror จากพัสดุเพื่อให้งานเดิมเชื่อมต่อได้ พัสดุเก่าที่ส่งแล้วใช้ snapshot รายการเดิม ส่วนบิลสะสมชี้พัสดุล่าสุด

`ready_to_ship` ต้องมีรายการที่ชำระครบ ที่อยู่ครบทุกระดับ และที่อยู่ที่ลูกค้าหรือผู้ดูแลยืนยันแล้ว ถ้ามียอดเพิ่มจนค้างชำระ หรือแก้รายการ/ที่อยู่/Tracking หลังเตรียมฉลาก ระบบล้างสถานะพิมพ์และให้เตรียมฉบับใหม่ พิมพ์หรือ Export จากชุดเดิมที่ข้อมูลเปลี่ยนแล้วจะถูกปฏิเสธ รวมถึงการ retry หลัง HTTP response สูญหาย

“ลบรายการที่เลือก” เป็น soft cancel ของพัสดุ ไม่ลบออเดอร์ สลิป หรือยอดรับเงิน สามารถคืนรายการก่อนส่งได้ รายการที่ส่งแล้วแก้ไข ยกเลิก หรือย้ายยอดจาก Shipping ไม่ได้ การส่งจริงต้องมี Tracking และขนส่ง กรณียกเลิกพัสดุที่จองกับผู้ให้บริการไปแล้ว ให้จัดการกับผู้ให้บริการโดยตรงด้วย

## รับที่อยู่จาก Messenger

Webhook ที่ตรวจลายเซ็นแล้วบันทึกข้อความก่อนแยกที่อยู่ ใช้ Regex ภาษาไทยที่คัดลอกเฉพาะข้อมูลในข้อความ รองรับตัวเลขไทย, +66, ต./อ./จ. และ แขวง/เขต/กรุงเทพฯ หากข้อความล่าสุดยังไม่ครบ จะลองรวมข้อความลูกค้าล่าสุดไม่เกิน 6 ข้อความใน 30 นาที โดยไม่คาดเดาจังหวัด รหัสไปรษณีย์ หรือชื่อที่หายไป

เมื่อมีพัสดุชำระครบและยังไม่ส่ง ระบบบันทึกชื่อ โทร ที่อยู่ ตำบล/แขวง อำเภอ/เขต จังหวัด และรหัสไปรษณีย์ทันที พร้อมส่งข้อความทวนและปุ่ม “ยืนยันที่อยู่” พัสดุยังไม่พร้อมส่งจนกว่าจะยืนยัน ปุ่มผูกกับ candidate ID ของที่อยู่นั้น ถ้ามีที่อยู่ใหม่เข้ามา ปุ่มของที่อยู่เก่าใช้ยืนยันที่อยู่ใหม่ไม่ได้ การพิมพ์ “ยืนยันที่อยู่” ต้องอยู่หลังการส่งข้อความทวนสำเร็จ

ที่อยู่ที่อ่านไม่ครบหรือมีเบอร์/รหัสไปรษณีย์ขัดแย้งกันจะไม่ถูกบันทึกโดยเดา ผู้ดูแลกรอกและตรวจยืนยันได้ในหน้า Shipping เมื่อบอทพักหรือร้านปิดตอบอัตโนมัติ ระบบยังบันทึกข้อมูลที่อ่านได้ แต่ไม่ส่งข้อความแทนผู้ดูแล การส่งข้อความใช้เงื่อนไข Messenger window, opt-out, kill switch, โควตา และ durable delivery ของระบบเดิม ข้อความที่มีที่อยู่พร้อมรูปสลิปยังผ่านการตรวจสลิปตามปกติ

## CSV สำหรับขนส่ง

ใช้ UTF‑8 BOM, CRLF, quote ทุกช่อง และ escape ข้อความที่อาจเป็นสูตร Excel มี 10 คอลัมน์ตามที่กำหนด:

1. ชื่อผู้รับ (Recipient Name)
2. เบอร์โทรศัพท์ (Phone Number)
3. ที่อยู่จัดส่งฉบับเต็ม (Address)
4. ตำบล/แขวง (Subdistrict)
5. อำเภอ/เขต (District)
6. จังหวัด (Province)
7. รหัสไปรษณีย์ (Zipcode)
8. รายการสินค้า/เลขออเดอร์ (Items / Order ID)
9. ยอดเก็บเงินปลายทาง COD — **0 ทุกแถว**
10. หมายเหตุ (Remark)

เบอร์โทรเป็นข้อความตัวเลขปกติที่ขึ้นต้น 0 สำหรับระบบนำเข้าขนส่ง ไม่สร้างสูตร `="081..."` หากเปิดใน Excel ให้ใช้ Data → From Text/CSV แล้วตั้งคอลัมน์เบอร์โทร/รหัสไปรษณีย์เป็น Text เพื่อรักษาเลขศูนย์ต้น การจับคู่คอลัมน์กับหน้ารับไฟล์ของผู้ให้บริการทำในระบบขนส่งนั้น

ปุ่ม Bee Move เป็นหน้าตัวเลือกเตรียม CSV และฉลาก ไม่มี API booking หรือการจองรถ ฟิลด์ API Key แสดงแบบ disabled และยังไม่รับหรือบันทึก Secret ตัวเลือกขนส่งบนหน้าส่งต่อใช้ตั้งชื่อไฟล์; ชื่อขนส่งบนฉลากยึดตามข้อมูลผู้รับแต่ละรายการ

## พิมพ์และทดสอบกับเครื่องจริง

- สติกเกอร์: ตั้งกระดาษ **100 × 150 mm**, Scale 100%, ปิด Headers/Footers และไม่เพิ่ม margin จากไดรเวอร์ นี่คือขนาด 100×150 มม. ตามที่กำหนด ไม่ใช่ 4×6 นิ้ว 101.6×152.4 มม. หากเครื่องใช้ preset 4×6 ให้สร้างขนาดกระดาษ 100×150 เอง
- A4: กระดาษ A4 แนวตั้ง สี่ฉลากต่อหน้า ขอบ 8 มม. Scale 100% ปิด Headers/Footers ฉลากย่อให้ลงสี่ช่องของ A4 ได้โดยไม่ล้น
- ใช้ปุ่ม **พิมพ์ / บันทึก PDF** บนเว็บ ระบบตรวจยอด ที่อยู่ และผู้ส่งล่าสุดก่อนเปิดหน้าต่างพิมพ์ การกด Ctrl+P ข้ามขั้นตอนนี้จะพิมพ์ข้อความให้กลับมาใช้ปุ่มแทนฉลาก
- `label_printed_at` คือเวลาที่กดเปิดหน้าต่างพิมพ์ ไม่ใช่หลักฐานว่าเครื่องพิมพ์พิมพ์ออกแล้ว การกดยกเลิกในหน้าต่างระบบไม่สามารถตรวจได้อย่างน่าเชื่อถือ จึงแสดงคำอธิบายไว้บนหน้าพิมพ์
- ฉลากแสดงรายการจัดของสรุปไม่เกินห้ารายการ พร้อมจำนวนรายการที่เหลือ ดูรายการเต็มและ UUID ออเดอร์ได้ในหน้า Shipping และ CSV QR เป็นเลขพัสดุภายใน SnapBot สำหรับอ้างอิงรายการจัดของ ไม่ใช่บาร์โค้ดรับฝากจากขนส่ง
- ข้อความยาวเกินพื้นที่จะถูกบล็อกก่อนเปิดพิมพ์ เพื่อไม่ตัดที่อยู่ผู้รับ ชื่อสินค้าและหมายเหตุบนฉลากเป็นข้อความสรุป

`npm run test:shipping:ui` ใช้ Chromium สร้างไฟล์จริงใน `.tmp/shipping-ui-preview/`:

- `shipping-100x150mm.pdf` — ข้อมูลจำลอง 5 พัสดุ / 5 หน้า
- `shipping-A4-four-up.pdf` — ข้อมูลจำลอง 5 พัสดุ / 2 หน้า โดยหน้าแรก 4 รายการ
- `downloads/snapbot-Bee-Move-shipping.csv` — ไฟล์ที่ดาวน์โหลดจาก flow จริงในเบราว์เซอร์ด้วยข้อมูลจำลอง
- ภาพหน้า Dashboard ที่ 375/768/1024/1440px และภาพหน้าพิมพ์

ทดสอบ page count, PDF MediaBox, ข้อความไม่ล้น, อ่าน QR กลับ, แก้ผู้รับ/Tracking, ส่งออก CSV และการปฏิเสธฉลากเก่าแล้ว การพิมพ์ด้วยเครื่อง Thermal จริงยังต้องเลือกไดรเวอร์และขนาดกระดาษที่ร้านใช้งานเอง

## ขอบเขตความปลอดภัยและตรวจสอบ

API ทุกตัวตรวจ session ผู้ใช้และสิทธิ์ร้านก่อนอ่าน/เขียนข้อมูลส่วนบุคคล คำขอเขียนตรวจ Origin มี rate limit, request UUID ป้องกันทำซ้ำ และ optimistic revision สำหรับแก้ผู้รับ การทำรายการหลายพัสดุเป็น Transaction: ถ้ารายการใดไม่ผ่านเงื่อนไขจะไม่บันทึกส่วนที่เหลือ มี audit receipt และ snapshot ของทุกชุดพิมพ์/Export ตาราง Shipping ไม่เปิดให้อ่านหรือเขียนโดย browser role โดยตรง Trigger ที่ต้องอ่านตารางส่วนตัวจากการเปลี่ยนสถานะออเดอร์เดิมใช้ definer ที่ล็อก search_path และไม่เปิดสิทธิ์เรียกตรงแก่ผู้ใช้

`npm run test:shipping` ทดสอบ parser, CSV injection, authorization, Webhook/deduplication และ Transaction ใน PostgreSQL จำลอง รวมรับเงินบางส่วน, รวมหลายองค์, ที่อยู่เก่า, ฉลาก stale หลัง retry, ส่งแล้วซื้อเพิ่ม, standalone order, soft cancel/restore, RLS และการรักษายอดรับเงินเดิม

ยังไม่ได้รัน migration บน Production ไม่ได้ส่ง Messenger จริง และไม่ได้เรียก API ขนส่งในการทดสอบ
