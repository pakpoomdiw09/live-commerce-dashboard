# การตรวจข้อมูลและกู้คืนกฎของร้าน

## ติดตั้ง

รัน `supabase/store-rules-validation.sql` หลัง `store-rules.sql` และ `store-rule-items.sql` ก่อนนำโค้ดชุดนี้ขึ้นใช้งาน ไฟล์รันซ้ำได้ ไม่แก้ไขหรือลบข้อมูลปัจจุบันและประวัติเดิม ไม่เรียกผู้ให้บริการ AI และไม่เปลี่ยนโควตา

## รูปแบบที่รองรับ

ข้อมูลเก่าแบบข้อความ รวมถึงข้อความที่กล่าวถึงคำว่า `snapbot_store_rules` และฟอร์มหัวข้อย่อยรุ่นเดิม ยังคงอ่านได้โดยไม่มีการย้ายหรือบันทึกใหม่อัตโนมัติ

เอกสารรายการกฎต้องมี `snapbot_store_rules: 1` และ `rules` เป็น array ไม่เกิน 200 ข้อ แต่ละข้อมี `id` ที่ไม่ว่างและไม่ซ้ำ กับ `body` ที่ไม่ว่าง โดยรองรับ `category` จากหมวดหมู่ที่กำหนดและ `enabled` แบบ boolean เป็นข้อมูลเสริม กฎรุ่นเดิมที่ไม่มีข้อมูลเสริมยังใช้งานได้ ไม่ยอมรับฟิลด์อื่น รุ่นเอกสารที่ไม่รองรับ หรืออักขระข้อความที่จัดเก็บไม่ได้ ขนาดรวมข้อมูลจัดเก็บไม่เกิน 50,000 ตัวอักษรตามขีดจำกัดของหน้าจอ

## การอ่านและการแสดงผล

`parseStoreRules` คืนสถานะ `empty`, `legacy`, `items` หรือ `invalid` พร้อม `issues` ที่มี `path`, `code` และข้อความภาษาไทย การอ่านข้อมูลเสียไม่โยนข้อผิดพลาดและไม่แปลงข้อมูลเสียนั้นเป็นข้อความให้ AI ใช้

หน้ากฎใช้สถานะดังกล่าวเลือกแสดงตารางหรือหน้ากู้คืน และมี error boundary เฉพาะส่วนเพื่อไม่ให้ข้อผิดพลาดในการเรนเดอร์ทำให้แดชบอร์ดทั้งหน้าหยุดทำงาน ฝั่ง AI ปฏิเสธกฎที่ไม่ถูกต้องก่อนจองโควตาหรือเรียกผู้ให้บริการ

## ทุกช่องทางบันทึก

- API หลักรับข้อความเดิมหรือฟอร์มเดิมโดยตรวจเอกสารและขนาดก่อนบันทึก
- API เพิ่ม แก้ไข ลบ และเปิด/ปิดกฎ ตรวจข้อมูลใหม่และข้อมูลเดิม ไม่สร้างรายการว่างทับเอกสารที่อ่านไม่ได้
- API คืนค่าจากประวัติปฏิเสธประวัติที่รูปแบบไม่ถูกต้อง โดยไม่ลบประวัตินั้น
- ช่องทดสอบตอบและหน้าตั้งค่าเดิมตรวจข้อมูลก่อนส่งคำขอ
- trigger ฐานข้อมูลตรวจข้อมูลเมื่อมีการเปลี่ยนกฎจริง ครอบคลุมทั้ง RPC และการเขียนผ่าน Supabase โดยตรง การแก้ค่าตั้งค่าอื่นที่ไม่เปลี่ยนกฎเก่าไม่บังคับลบกฎที่มีปัญหา

การแก้ไขจะเก็บค่ากฎเดิมไว้ใน `agent_prompt_versions` หากยังไม่มีสำเนาตรงกันในประวัติ ก่อนบันทึกค่าใหม่ในธุรกรรมเดียวกัน ไม่มีการปรับข้อความเดิม ตัดรายการที่ไม่ผ่าน หรือเลือกเก็บเฉพาะบางข้อโดยอัตโนมัติ

## การกู้คืน

หน้ากู้คืนแสดงต้นฉบับแบบอ่านอย่างเดียว พร้อมปุ่มดาวน์โหลดไฟล์ข้อความและโหลดข้อมูลใหม่ ผู้ดูแลที่มีสิทธิ์สามารถแก้ต้นฉบับเป็นเอกสารกฎที่ถูกต้องหรือข้อความกฎแบบเดิมได้ ต้องยืนยันว่าต้องการแทนที่ก่อนส่งคำขอ

API หลักต้องได้รับ `recover: true` พร้อม `expectedInstructions` ที่ตรงกับข้อมูลปัจจุบันเมื่อต้นฉบับเสีย ฟังก์ชัน `save_validated_store_rules` ตรวจสิทธิ์เจ้าของร้านและเปรียบเทียบข้อมูลเดิมภายใต้ database lock หากมีผู้แก้ระหว่างนั้นจะคืน 409 และเก็บฉบับแก้ไขบนหน้าจอให้ผู้ใช้ตรวจสอบต่อ

ข้อผิดพลาดส่งกลับในรูป `{ error, code, issues? }` โดย `error` เป็นข้อความภาษาไทย รหัสที่เกี่ยวข้องคือ `STORE_RULES_INVALID`, `STORE_RULES_RECOVERY_REQUIRED` และ `STORE_RULES_CONFLICT`

