# Highest-bid winner confirmation

Auction comments are handled before CF matching. Numeric bids update the active round's highest bidder/price using the existing minimum and increment rules. Both tag lists come from current `live_sessions.auction_settings`, falling back to the round snapshot when no session settings exist. Confirmation defaults to `1` and admin closing defaults to `ปิด` only when the corresponding configured list is empty or undefined. Custom tags replace defaults and match the entire comment after Unicode, case, whitespace and emoji-selector normalization.

Only the recorded highest bidder can confirm. An admin closing tag closes bidding and locks that bidder/price without creating an invoice. Supabase then accepts the winner's confirmation on the active or locked round, validates Page/tenant/post, new-comment eligibility and receipt ordering, and atomically creates the invoice and delivery outbox. A locked winner can confirm even after the next round opens. The winning item price comes from `auctions.current_price`; configured shipping remains a separate bill charge. Wrong-sender confirmations, ties, duplicate comments and late bids cannot create another invoice. Historical on-demand self-billing is no longer a confirmation path.

After commit the webhook immediately drains the winner outbox. The private reply includes item name, winning price, shipping, outstanding balance, bank account and a signed QR/payment/slip-upload link. Confirmed winners receive one complete message regardless of the older split-summary setting. Existing pending legacy deliveries retain their recovery behavior. Failed/uncertain sends retain the durable outbox review safeguards. Page credentials, an active bank account, payment-link configuration and enabled private replies are required for delivery.

Deploy `supabase/live-auction-highest-confirmation.sql` after `live-auction-on-demand.sql`, followed by `supabase/live-auction-dynamic-tags.sql`, before deploying the matching application change. Both are rerunnable, do not send messages, and are included in the generated fresh-install/upgrade bundles. Historical invoices stay intact.

Validation: `npm.cmd test`, `npm.cmd run test:auctions`, `npm.cmd run test:schema`, `npm.cmd run build`.

## Shared Facebook comment configuration

Apply `supabase/facebook-comment-configuration.sql` after `live-auction-dynamic-tags.sql` and `live-cf-order-post.sql` before deploying the updated handler. The generated schema bundles include it. This migration has not been applied to a hosted database by this change.

The configuration migration installs explicit auction resolver, allocation and finalizer definitions on the existing commerce/auction schema. It can repair missing or older resolver bodies without inspecting their source text and can be rerun directly. Compatible function identities and dependencies are retained; incompatible argument names, return types or defaults are recreated without `CASCADE`. RPC execution is explicitly restricted to `service_role` after installation.

Each eligible comment resolves the tenant/Page/post session in Supabase. Explicit `live_sessions.mode` selects `auction`, `cf`, or `auto`. Legacy sessions infer auction ownership from existing rounds; other posts use CF plus general ingestion. Auction ownership prevents numeric bids and confirmations reaching CF even when no round is active. Auto mode runs only inbox ingestion and general comment rules.

The dashboard's `auction_settings.keywords` and `closeKeywords` take precedence. Both TypeScript and SQL then check flat session keywords, session canonical/tag aliases, comment-settings aliases/keywords, and auction-settings aliases; the same order is used for the round snapshot only after session sources are exhausted. Every candidate is normalized and empty/invalid arrays are skipped. Centralized defaults apply only when no configured source contains usable tags. Optional opening and counting commands require configured `opening_tags`/`counting_tags`; they have no implicit vocabulary. Matching normalizes Unicode, whitespace, case and emoji selectors.

Owners can persist configuration through `POST /api/live-cf/sessions` with `{tenantId, sessionId, requestId, action: "comment-config", settings: {...}}`. `requestId` is a UUID. Settings accept `mode`, tag arrays, `opening_tags`, `counting_tags`, `countEnabled`, `publicReply`, `privateReply`, `public_reply_template`, `private_reply_template`, and `cf_patterns: [{code, keywords, match_mode: "strict" | "flexible"}]`. Dashboard tag lists govern matching while populated; clearing one source falls through to remaining aliases/snapshots. Defaults return only after every configured source is empty. The RPC validates ownership and session tenancy; browser roles cannot call it directly.

CF rules retain precedence; otherwise active tenant catalog product/variant codes and session patterns are matched atomically. Ambiguous matches do not order. Stock reservation and comment idempotency use the existing order core; `live_post_id` is stamped before order insertion. Sent private replies are checkpointed separately from local Inbox history, so history retries do not resend Messenger messages. General inquiries also sync into Inbox without creating an order.

Stored templates support `{customer_name}`, `{item_name}`, `{price}`, `{total_amount}`, and `{bank_account}` alongside existing token names. `{price}` is the item price; `{total_amount}` is the pending bill total. Substitution is single-pass, so customer text cannot inject another template token. Payment links and required auction payment facts remain available in the final bill.
